# full-review

変更したコードを、次の3つの観点からレビューする。

1. バグ（`/code-review`）
2. 品質の改善（`/simplify`）
3. 標準機能・既存ライブラリへの置き換え（このスキル独自の観点）

**このスキルは、ユーザーの承認なしにコードを修正しない。** Phase 6 より前に、ファイルを編集してはならない。

このスキルはメインの会話で実行する。サブエージェントの中では実行しない。`/code-review` と `/simplify` は内部でサブエージェントを並列に起動するため、入れ子になると並列起動が使えなくなる。

## Phase 0 — 準備

1. **対象を決める。** 引数があれば、それを対象にする（PR 番号、ブランチ名、パス）。なければ現在のブランチの変更を対象にする。対象の diff は次の順で取得する。
   - `git diff @{upstream}...HEAD`。upstream がなければ `git diff main...HEAD`
   - 未コミットの変更があれば `git diff HEAD` も含める
2. **作業ツリーの状態を記録する。** Phase 4 で比べるために、次の出力を控えておく。

   ```bash
   git status --porcelain
   ```

   ```bash
   git diff HEAD | shasum
   ```

3. **技術スタックを調べる。** 依存関係の定義ファイルを読み、言語・フレームワーク・ライブラリと、その**バージョン**を把握する。例：`composer.json`、`package.json`、`go.mod`、`pyproject.toml`、`requirements.txt`、`Gemfile`、`Cargo.toml`、`pom.xml`、`build.gradle`。lock ファイルがあれば、実際に入っているバージョンはそちらで確認する。
4. **プロジェクトのルールを読む。** リポジトリと変更ファイルの上位ディレクトリにある `CLAUDE.md` を読む。設計方針（層構造、「現状の動作を変えない」などの原則）は、Phase 3 と Phase 5 の判断に使う。

## Phase 1 — バグのレビュー（/code-review）

Skill ツールで `code-review` を呼び出す。引数は `medium <対象>` とする（対象がなければ `medium` だけ）。

- `--fix` は付けない。
- `max` と `ultra` は使わない。ユーザーが明示的に指定した場合だけ使う。

結果の指摘を、観点「バグ」として控えておく。

## Phase 2 — 品質のレビュー（/simplify）

`/simplify` は、手順の最後で修正を作業ツリーに適用する。このスキルでは修正させない。呼び出す前に、次の制約を自分に課すこと。

> `/simplify` の手順は **Phase 1（レビュー）までだけ実行する。** Phase 2「Apply the fixes」は実行しない。Edit・Write・ファイルを書き換えるシェルコマンドは使わない。レビュー役のエージェントにも「指摘だけ返し、ファイルは編集しない」と伝える。指摘は一覧として返す。

そのうえで、Skill ツールで `simplify` を呼び出す（対象があれば引数に渡す）。結果の指摘を、観点 reuse / simplification / efficiency / altitude として控えておく。

## Phase 3 — 標準機能・既存ライブラリへの置き換え調査（alternatives）

変更されたコードのうち、**自前で実装している処理**を探す。それぞれについて、もっと良い実装手段がないかを調べる。

### 3-1. 候補を探す順番

次の順で探す。上にあるものほど、導入の負担が小さい。

1. **言語の標準機能・標準ライブラリ**（組み込み関数、標準のデータ構造、新しい構文など）
2. **フレームワークの標準機能**（バリデーション、認可、ORM、キャッシュ、キュー、ヘルパーなど）
3. **既に依存関係に入っているライブラリ**
4. **新しいライブラリ**（最後の手段。下の「新しいライブラリの扱い」に従う）

### 3-2. 調べ方

- **バージョンを必ず合わせる。** Phase 0 で調べたバージョンで、その機能が使えるかを確認する。新しい版にしかない機能は提案しない（提案する場合は「バージョンアップが必要」と明記する）。
- **ドキュメントで確かめる。** 記憶だけで判断しない。context7 などのドキュメント取得ツールがあれば、それで公式ドキュメントを引く。なければ WebSearch / WebFetch で公式ドキュメントを確認する。
- **プロジェクト内の前例を探す。** 同じ処理を既に標準機能で書いている箇所があれば、それを根拠として示す。

### 3-3. 比べる観点

今の実装と候補を、次の観点で比べる。

| 観点 | 見る点の例 |
|---|---|
| 安全性 | インジェクション（SQL・コマンド・HTML など）、一括代入、認可の抜け、入力検証、秘密情報の扱い、エラーの握りつぶし、競合状態 |
| 効率性 | 計算量、繰り返しの I/O、N+1 クエリ、不要なメモリ確保、キャッシュの有無 |
| 可読性 | コード量、意図の明確さ、ネストの深さ、命名 |
| 保守性 | テストのしやすさ、フレームワークの更新への追従、他のメンバーが知っている書き方か |

### 3-4. 提案する条件

次の両方を満たすものだけを提案する。

- **メリットが大きい。** 少なくとも1つの観点で明確に良くなり、他の観点で悪くならない。好みの違い程度の差は提案しない。
- **動作が同じになる。** 動作が変わる場合（エラー時の挙動、戻り値の型、空の入力の扱いなど）は、提案はしてよいが、何が変わるかを必ず書く。

### 3-5. 新しいライブラリの扱い

新しいライブラリは、1〜3で解決できず、メリットが特に大きい場合だけ提案する。提案するときは、次を添える。

- ライセンス
- メンテナンス状況（最終リリース日、利用の広さ）
- 追加される依存の大きさ

依存関係のファイルは、このスキルの中では変更しない。

## Phase 4 — 作業ツリーが変わっていないかの確認

Phase 0 と同じコマンドを実行し、記録と比べる。

- **同じなら：** そのまま Phase 5 へ進む。
- **違うなら：** レポートの冒頭で「レビュー中にファイルが変更された」と警告し、変更されたファイルを `git diff` で示す。**自動で元に戻さない。** ユーザーの未コミットの変更まで消す危険があるためである。戻すかどうかはユーザーに決めてもらう。

## Phase 5 — 統合レポート（HTML）

Phase 1〜3 の指摘をまとめ、HTML レポートとして出力する。

### 5-1. 指摘を整理する

1. **重複をまとめる。** 同じ箇所・同じ仕組みを指す指摘は1つにし、報告元をすべて残す。
2. **観点を決める。** 各指摘を、次のどれか1つに分類する。並び順もこの順にする。
   1. バグ（`bug`）
   2. 安全性（`sec`）
   3. 効率性（`perf`）
   4. 可読性・保守性（`maint`）
3. **番号を付ける。** 並べた順に `#1` から通し番号を付ける。
4. **報告元を記録する。** 報告元のエージェント名は英語で、次のどれかにする。
   - `code-review`：Phase 1
   - `simplify`：Phase 2
   - `alternatives`：Phase 3（標準機能・既存ライブラリへの置き換え調査）
5. **注意点を記録する。** 該当するものだけ記録する。
   - `動作の変化あり`：直すとプログラムの動きが変わる
   - `方針と衝突`：PR 本文や `CLAUDE.md` に書かれた方針と合わない（例：「現状の動作を変えない」範囲で動作が変わる提案）
   - `要確認`：バグかどうか判断できない。仕様の確認が必要
   - 動作が変わらない場合は、何も記録しない
6. **評価を記録する。** 「今は直さなくてよい」「別チケットで扱う」などの判断があれば、文章で記録する。チップにはしない。

### 5-2. HTML を作る

このスキルと同じフォルダーにある `report-template.html` を Read ツールで読み、それを元に作る。

- **構成は次の3つだけにする。** 順番も変えない。
  1. **PR の内容**：次の順に書く。PR でない場合は、ブランチ名やパスを対象名にする。
     - 概要：PR が何をするか、変更前はどうだったか（2〜3文）
     - 対象（リポジトリ、PR 番号、変更ファイル数、追加・削除行数）、ブランチ、技術スタックとバージョン
     - 作成者の方針（PR 本文や `CLAUDE.md` に書かれているときだけ）
     - **クラスの関係**：変更に関係するクラス・関数と外部システム（DB、外部 API など）の関係を、mermaid の `flowchart LR` で描く。矢印は「呼び出す・使う」。各ノードには名前と役割を短く書く。
     - **処理の流れ**：処理を ①〜 の番号付きの手順にし、mermaid の `flowchart TD` で描く。スキップや失敗時の分岐も描く。手順は3〜10個にする。
     - **各手順の詳細**：図と同じ番号で、処理名・担当（`Class::method()`）・内容の表にする。内容には、指摘を理解するのに必要なこと（API の呼び出し方、設定値、例外の扱い、リトライの条件など）を書く。複数の手順で使う処理（認証、リトライなど）は「共通」の行にする。
     - 処理の流れが無い変更（設定ファイルだけの PR など）では、クラスの関係・処理の流れ・各手順の詳細を省く。
  2. **指摘件数**：4つの観点ごとの件数。
  3. **指摘の一覧**：観点ごとのセクションに、指摘カードを番号順に並べる。指摘が0件の観点はセクションごと削除する。
- **`<style>` とアイコンの定義は変更しない。** 中身だけを埋める。テンプレートのコメントは、公開する前にすべて削除する。
- **チップの付け方**
  - 報告元は `chip agent`（エージェントのアイコン付き）。報告元が複数なら並べる。
  - 注意点は `chip warn`（注意のアイコン付き）。「動作の変化なし」のチップは付けない。
  - チップはこの2種類だけにする。優先度や判断は、本文の「評価」に書く。
- **指摘カードの見出し**
  - タイトル：「どこで、何が起こるか」を1つの文で書く。
    - 「どこで」は処理の名前で書く（例：「一時シートの作成」「同期先シートへの反映」）。手順の番号やコロンは使わない。
    - 「何が起こるか」は、利用者や開発者に見える結果で書く。コードの状態（「自前で実装している」「分散している」など）では書かない。
    - 起きる条件があれば、「〜すると」「〜で」で文の中に入れる。
    - 読みやすさのための読点は使ってよい。ただし、2つの文を読点でつなげない。
    - 原因や直し方は書かない（本文に書く）。
    - 例：「一時シートの作成がタイムアウトすると、成功していても同期が失敗になる」「同期先シートへの反映で、右側に手で追加した列まで毎晩消える」
  - 「処理」の行：その指摘が「各手順の詳細」のどの手順に当たるかを、番号と処理名で書く（例：「④ 一時シートを作る」）。すべての指摘を、どれかの手順か「共通」に結び付ける。
  - 「何が起きるか」：最初に、該当するコードの役割と今の動きを説明する。PR の処理を知らない人が、このレポートだけで修正するかどうかを判断できるようにする。そのあとで、問題が起きる条件と結果を書く。
  - 本文：「何が起きるか」「なぜ問題か」「どう直すか」は必須。「動作の変化」は変化があるときだけ。「評価」は判断を添えるときだけ。「根拠」は `alternatives` の指摘では必須。
  - 手順で起きる問題は、番号付きの手順で書く。
  - 直し方は、可能なら数行のコード例を付ける。
- **文章のルール**
  - 読み手は、基本的な技術用語を理解しているエンジニアと想定する。用語集や用語の説明は書かない。
  - 一文を短く保つ。比喩やたとえ話は使わない。
  - 数値は、根拠があるものだけ書く（PR の実測値、ライブラリのバージョンなど）。
  - 取得して確かめていない資料は、根拠に「未確認」と書く。
- **フッター**：Phase 4 の結果を書く。変化がなければ「レビュー中にファイルは変更していません。」とする。

### 5-3. 公開する

- ファイルはスクラッチパッドに `<対象名>-full-review.html` として保存する（例：`pr811-full-review.html`）。
- Artifact ツールで公開する。公開の前に、Artifact のページ作成の決まり（`artifact-design` スキル、または quickstart の結果）を確認する。
- 同じ対象をもう一度レビューしたときは、同じファイルパスで公開し直し、URL を変えない。
- チャットには、観点ごとの件数、重要な指摘の要約（バグと安全性の見出し）、URL だけを出す。指摘の全文はチャットに書かない。
- 指摘が1つもなければ、HTML は作らず、チャットで「指摘なし」と伝える。

## Phase 6 — 修正（承認後のみ）

レポートのあと、どの番号（HTML レポートの `#番号`）の指摘を修正するかをユーザーに尋ねる。

- ユーザーが選んだ指摘だけを修正する。
- 修正後、プロジェクトのテストコマンドがあれば実行し、結果を報告する。テストの実行方法は `CLAUDE.md` や README で確認する。
- ユーザーが何も選ばなければ、修正せずに終わる。
